## 2. Layout and component boundaries
- Root app layout owns metadata, global CSS and document language.
- Workspace route group is protected by a server-side Supabase Auth user check. The Next.js 16 Proxy refreshes cookie sessions; the workspace layout calls `auth.getUser()` before rendering. Tenant membership and resource authorisation are separate future tasks and are not implied by authentication.
- Auth route group implements email/password sign-in and local sign-out through server actions. Open registration is intentionally disabled.
- Module routes resolve only through the canonical A–M registry. Unknown module slugs return the application not-found boundary.
- WorkspaceShell owns navigation, mobile menu state and route-aware active state.
- ModuleLanding owns the common module entry presentation and explicitly communicates non-operational status.
- Domain services, data access, auth and provider calls do not belong in presentation components.

## 3. Security and legal-trust limits
- The application has a real identity-provider boundary, but no user profile, organisation, workspace, membership, matter, document or evidence schema is connected. Authentication alone does not grant tenant or resource access.
- The health route returns connection flags and never returns secrets or environment values.
- Error boundary logging records only error name and digest; it does not log legal content or user data.
- Robots indexing is disabled in metadata for this non-production foundation shell.
- No client-side value is treated as proof of identity, tenant or matter permission.
- Phase 1 still must add principal/profile mapping, tenant/workspace resolution, membership, role and permission checks, RLS, private storage and audit controls before any confidential matter or document data is connected.

## 4. Dependency and package baseline
The app package pins Next.js 16.4.5, React 19.3.1, Tailwind CSS 4.3.5, TypeScript 5.9.3, `@supabase/ssr` 0.12.7 and `@supabase/supabase-js` 2.119.0. The npm lockfile is generated by a network-enabled GitHub Actions workflow and verified with `npm ci`. The npm lockfile is generated and committed as part of task 0.12 CI verification. Runtime packages are isolated in apps/web; the repository's foundation CI tooling remains at the root.

## 5. Deferred implementation
User profile/principal mapping, organisations/workspaces, memberships/invitations, RBAC, RLS, private storage, audit, queues, AI providers, legal-source retrieval, evidence processing, reasoning, verification, document drafting and operational workflows remain assigned to their numbered phases. This shell is a real route/layout implementation, not a claim that those features are already operational.
