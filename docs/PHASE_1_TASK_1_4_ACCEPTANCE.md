## 1. Delivered implementation

### Principal and identity

- A stable internal principal is distinct from the Supabase Auth user ID.
- A private provider-subject mapping links the Supabase identity to the internal principal.
- Provider, provider subject, Auth user ID and principal ownership cannot be changed through ordinary update operations.
- The current-principal resolver returns a principal only while its account status is `active`.
- Suspended and deactivated principals therefore fail the profile RLS boundary.

### Profile data

The public `user_profiles` table contains presentation data only:

- display name
- given name
- family name
- avatar URL
- locale
- IANA time zone
- creation and update timestamps

Email and authentication credentials remain in Supabase Auth. Profile forms and Server Actions do not accept a principal ID, provider subject, role, status or permission field.

### Validation and database enforcement

- Avatar URLs are parsed and must use HTTPS; embedded credentials and oversized values are rejected.
- Locale values are validated and default to `en`.
- Time zones are validated against supported IANA identifiers in the application and database.
- Profile ownership is immutable.
- Authenticated users receive only the required profile-column update grants.
- RLS enforces per-principal profile access with both update visibility and row checks.
- Privileged trigger paths use an empty search path and fully qualified object names.
