# Phase 1.8 — PostgreSQL RLS and private Storage design

- **Status:** Implementation in progress; batch verification deferred by owner instruction
- **Date:** 10 November 2026
- **Depends on:** Tasks 1.1–1.7 implementation
- **Database target:** dedicated Njumeni Supabase project `vvjpsejeeffykaozfbik`
- **Deployment boundary:** local migration replay and synthetic-principal tests only; no hosted schema deployment.

## 1. Objective

Enforce tenant and workspace boundaries at the PostgreSQL and Supabase Storage layers. Every storage object is private, scoped to an existing active organisation and workspace, and authorised through the caller's current permission grants. Client-side filtering and signed URLs are not substitutes for these database policies.

## 2. Storage namespace

The first private bucket is `njumeni-workspace-files`. It is private and has a 50 MiB object-size limit. The initial MIME allow-list includes PDF, common Office documents, plain text, CSV, JPEG, PNG and TIFF. Executable formats, HTML, SVG, archives and macro-enabled Office formats are not accepted in this initial bucket.

Object names use this exact structure:

```text
<organization-uuid>/<workspace-uuid>/<file-uuid>/<filename>
```

- The organisation UUID and workspace UUID are mandatory first and second path segments.
- The file UUID is generated by the server; the client does not choose tenant or workspace scope.
- The workspace must belong to the named organisation.
- Both workspace and organisation must be active.
- File names are display metadata only; access decisions never depend on them.
- The helper rejects malformed UUID segments, empty object IDs, control characters and path traversal segments.

## 3. Permission mapping

| Storage operation | Required permission |
|---|---|
| List/download/read metadata | `document.read` |
| Upload/create/replace in the same scope | `document.upload` |
| Delete | `document.delete` |

The permission evaluator also requires an active principal, active organisation, active workspace and active membership/role context. The immutable organisation owner receives the defined owner authority. An organisation membership without workspace membership does not grant access to workspace files.

## 4. Database enforcement

- The bucket is created or reconciled as `public = false`.
- RLS is explicitly enabled on `storage.objects`; policies permit only authenticated users and only the Njumeni bucket.
- A private security-definer helper validates the path, resolves the workspace-to-organisation relationship and calls the central permission evaluator.
- The helper has an empty search path, returns only a boolean, fails closed on malformed paths or unexpected errors, and is not executable by anonymous/public roles.
- SELECT, INSERT, UPDATE and DELETE are separate policies with operation-specific permission checks.
- An UPDATE must be authorised both for the existing and resulting object path; users cannot use an update policy to move an object into a scope where they lack upload authority.
- The application must not use public URLs for this bucket. Downloads use authenticated Storage API access or short-lived signed URLs generated only after the same workspace permission check.

## 5. Application integration contract

- `apps/web/src/lib/workspace-storage.ts` provides server-only upload-intent, short-lived download URL and delete operations.
- All storage keys are generated server-side from resolved organisation/workspace context and an opaque file UUID.
- Never accept an organisation ID, workspace ID, bucket name or storage key from the browser as proof of access.
- The server validates the active workspace and required permission before issuing upload/download operations through the `has_permission` RPC.
- Upload uses `createSignedUploadUrl` with `upsert: false`; downloads use a 60-second signed URL; delete requires `document.delete`.
- The browser receives only a short-lived upload/download capability for the exact object when a signed URL is needed.
- Do not persist signed URLs as document identity; persist bucket ID and object key.
- No service-role key is exposed to the browser.
- A file record and its object lifecycle must be coordinated by the document module in the later document phase; this task establishes the storage boundary only.

## 6. Synthetic verification coverage

The pgTAP suite provisions two separate synthetic tenant owners and verifies:
- correct tenant/workspace path is authorised;
- owner can create and read an object in its own workspace;
- a second tenant cannot read the first tenant's object metadata;
- a second tenant cannot insert into the first tenant's workspace;
- organisation/workspace mismatch is denied;
- malformed UUID/path values are denied without raising cast errors;
- unsupported permission keys are rejected;
- anonymous callers cannot execute the private helper;
- the bucket is configured as private.

The wider Task 1.11 isolation suite will add member, editor, reviewer, viewer, suspended/revoked membership, cross-workspace and API/signed-URL negative cases. Phase 1 closeout remains the production safety gate.

## 7. Explicit exclusions

- No public bucket or public object URL.
- No service-role browser upload.
- No cross-tenant sharing or external legal-document links.
- No content scanning, malware quarantine or OCR processing in this task; these belong to later document/evidence ingestion workflows.
- No hosted migration deployment.
- No real customer or confidential legal files in development tests.
