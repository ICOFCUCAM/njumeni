## 2. Positive design properties

The preliminary SQL and application code already aim to enforce several important boundaries:

- Internal principal identifiers are distinct from Supabase Auth user IDs.
- Provider-subject mapping is held in the non-API `private` schema.
- Authenticated users receive no direct table privileges on principals or provider identities.
- The profile is limited to presentation data; no role, status, tenant or permission fields are user-editable.
- Profile SELECT/UPDATE policies resolve the principal from the authenticated provider identity.
- UPDATE policy includes both `USING` and `WITH CHECK`.
- Profile update action calls `auth.getUser()` and does not accept principal/provider identifiers from form input.
- Profile UI is under the protected workspace route group and is dynamically rendered.

These are useful foundations, but static source-contract tests do not prove the actual database RLS, trigger or grant behaviour.

## 3. Required corrections before migration approval

### 3.1 Principal status must participate in identity resolution — implementation added

The current `private.current_principal_id()` helper returns the mapped principal without checking `private.principals.status`. That means a principal marked `suspended` or `deactivated` would still resolve for the profile RLS policies.

Before approval, change the lookup so it returns a principal only when its status is `active`. Add database tests proving:

1. Active principal can read and update only its own profile.
2. Suspended principal cannot read or update its profile.
3. Deactivated principal cannot read or update its profile.
4. A user cannot alter principal status or provider identity through the Data API.
5. A user cannot change the profile's `principal_id` or update another principal's row.

This profile-level check is not a substitute for the future central server-side account-status guard on every protected application operation. Record that as a cross-task security dependency.

### 3.2 HTTPS avatar URL validation must be consistent — application validation added

The application action accepts an HTTPS scheme case-insensitively, while the SQL check currently uses a case-sensitive `^https://` expression. Uppercase `HTTPS://` can pass application validation and then fail in PostgreSQL.

Choose one canonical validation rule and apply it consistently in the action and SQL constraint. Add tests for lowercase HTTPS, uppercase/mixed-case HTTPS, HTTP, malformed URLs, and maximum length. Consider parsing with the platform URL parser and requiring `protocol === 'https:'`, rather than relying only on a prefix regex.

### 3.3 Time-zone validation — application validation added

The current action and SQL only check that the timezone string is non-empty and within 100 characters. Validate that it is a supported IANA time-zone identifier before accepting it. Preserve a stable default (for example `UTC`) and test invalid names.

### 3.4 Trigger and SECURITY DEFINER review

The draft uses SECURITY DEFINER functions for Auth-user provisioning/deletion and principal resolution. These are privileged code paths and require a focused SQL security review:

- Keep functions in the non-exposed `private` schema.
- Keep `search_path = ''` and fully qualified object names.
- Revoke default PUBLIC/anon/authenticated execution where not required; verify trigger invocation remains valid after revocation.
- For the callable principal-resolution helper, require the caller's authenticated `auth.uid()` and prove that the function cannot return another user's principal.
- Verify trigger owner, grants, trigger firing and error behaviour on local Supabase.
- Verify Auth-user deletion cascades correctly without orphaning principal or profile rows.
- Run Supabase security advisors after local/hosted schema creation, before any production release.

## 4. Application integration test gaps

The current Node source-contract test checks selected source strings. It does not execute the Server Action or prove RLS. Add:

- Server Action tests for unauthenticated access, absent profile, malformed fields, failed update, successful update and redirect behaviour.
- Database integration tests for profile ownership and principal-status enforcement.
- A test proving the action cannot update another principal by tampering with form fields or URL parameters.
- A test for avatar URL and IANA timezone validation.
- Browser tests for the Profile Settings navigation, loading, save success, and save/error states after the migration is actually applied.

Do not enable the profile route in production before the corresponding schema exists and the migration has been applied through the approved deployment process.
